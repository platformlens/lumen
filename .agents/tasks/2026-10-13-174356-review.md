# AI settings auto-save fix: allowlist, validation, and Settings feedback

The commit (59594f4) targets the real root cause: `settings:set`/`settings:get` reject keys outside `SETTINGS_ALLOWLIST`, so `aiToolMode`, `aiTrustedCommands`, `local*`, `theme`, `notificationsMuted` and `geminiServiceTier` were never stored. The Settings.tsx half of the change is sound: saves are awaited, failures revert the UI and show an error card, `aiModelChanged` fires only after a successful save, and the provider toggle now picks a model that belongs to the new provider. The `electron/main.ts` half as committed is corrupted by a misapplied partial-stage patch: the allowlist entries and validation landed inside unrelated IPC handlers, and the real allowlist is unchanged.

Watch for: **confirmed** the committed `electron/main.ts` does not contain the fix and does not compile; the working tree does, so the stated "tsc clean" result does not describe the committed code.

**Verdict**: NEEDS_CHANGES

## High-level view

The persistence fix is the right shape: extend the allowlist, widen the value schema to `string[]`, validate the values that gate command execution, and keep the generic `settings:get/set` pattern so the written `settings_*` keys match what `main.ts` already reads per AI request. In the working tree this is correct and the full path (UI, preload, `settings:set`, `store.set`, and back through `settings:get` on mount) works.

The committed version of that main-process change is broken. The hunks were staged with stale line offsets, so they were inserted into `ai:startSession` and `ai:getCurrentSession` instead of the allowlist and `settings:set` handler. Only the `z.array(...)` value-schema hunk landed in the right place. At HEAD the tool-call bug is therefore not fixed (the allowlist still rejects `aiToolMode`), and the file has syntax and type errors.

The renderer changes are consistent with the project's glassmorphism styling and avoid `any`. Remaining gaps are minor and noted below.

## Settings.tsx persistence path

`persistAiSetting` never rejects, and `handleModelChange`, `handleToolModeChange` and `handleTrustedCommandsChange` revert on failure. `aiModelChanged` is dispatched only after a successful save, so `App.tsx` state (`aiProvider`/`aiModel`) and the main-process store stay in agreement. Mount-time loads of `aiToolMode` and `aiTrustedCommands` now log errors, which would have exposed the original allowlist rejection. The inline "Saved" indicator and red error card follow the theme rules (`text-green-400`, `bg-red-500/10 border-red-500/20 rounded-xl`).

The tool mode is read from `store.get('settings_aiToolMode')` per AI request in the main process, so the AI panel needs no extra wiring once the write succeeds. The validator restricting `aiToolMode` to `off|read|read-write` is appropriate given it gates kubectl execution. `theme` values (`blue|charcoal|red`) match the Settings UI, and `geminiServiceTier` (`standard|flex`) matches the `App.tsx` type.
